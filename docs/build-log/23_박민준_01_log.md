## 1. 계획과 위임

### 1.1 Realtime Voice 구조 파악

처음에는 OpenAI Realtime API를 담당하는 상황에서 다음 질문부터 시작했다.

- Realtime Voice API를 어떤 방식으로 연결해야 하는가?
- Twilio, GPT Realtime, 별도 GPT LLM은 각각 무엇을 담당하는가?
- Voicebox 또는 ElevenLabs의 복제 음성을 Realtime에 적용할 수 있는가?
- 다른 개발자와 합치기 쉬운 모듈 경계는 무엇인가?

Codex는 공식 OpenAI 문서를 조사해 역할을 다음처럼 분리했다.

```text
전화 사업자(Twilio/SIP) = 실제 전화번호, PSTN 발신, DTMF, 통화 연결
GPT Realtime             = 상대 음성 인식, 실시간 응답, 끼어들기 처리
별도 GPT LLM             = 업무 계획, 복잡한 판단, 사용자 확인 필요성 판단
MCP                      = 통화 작업 생성·조회·승인을 위한 제어 인터페이스
DB                       = 작업 상태, 승인, 대화 기록, 최종 결과 저장
```

Voicebox 음성을 OpenAI Realtime의 내장 `voice`에 직접 등록할 수는 없으며, 필요하면 Realtime의 텍스트 출력을 별도 TTS 계층으로 보내는 구조가 필요하다고 정리했다. 또한 GPT Realtime만으로 일반 전화번호에 발신할 수 없고 전화 사업자 또는 SIP 계층이 필요함을 확인했다.

### 1.2 MVP 범위 조정

기획서, PDF, FULL AUTO 수정 보고서를 검토하면서 초기 방향을 다음과 같이 좁혔다.

1. 사용자의 목표·조건·금지사항을 먼저 구체화한다.
2. 제한된 권한 안에서 AI가 통화를 진행한다.
3. 범위를 벗어난 결정만 사용자에게 다시 묻는다.
4. MCP는 음성 전송이 아니라 통화 작업을 제어한다.

이후 팀 내 역할이 Realtime Voice에서 웹 프론트엔드로 변경되었다. 사용자 피드백에 따라 서버·DB·전화 워커를 수정하지 않고 다음 프론트엔드 범위만 맡기로 했다.

- 자연어 또는 음성으로 요청 입력
- 전화 전 정보 확인
- ARS, 상담사 대기, 통화 중 사용자 확인 상태 표시
- 실시간 대화 기록 형태의 진행 화면
- 완료 결과와 전체 기록 표시
- 백엔드가 연결되기 전 사용할 데모 Gateway
- 실제 API가 준비됐을 때 교체 가능한 어댑터 경계

### 1.3 구현 계획

Codex가 세운 구현 순서는 다음과 같았다.

## 2. 구현 또는 조사 과정

### 2.1 도메인 계약과 데모 Gateway

먼저 프론트엔드가 다룰 예약 요청과 통화 상태를 타입으로 고정했다.

- `src/features/reservations/types.ts`: 예약 요청, 상태, 대화, 결과 타입
- `src/features/reservations/schema.ts`: 전화번호·날짜·필수값 검증
- `src/features/reservations/demo-timeline.ts`: ARS부터 완료까지의 데모 상태 전이
- `src/features/reservations/gateway.ts`: 데모 구현과 향후 API 구현을 분리하는 Gateway
- `schema.test.ts`, `demo-timeline.test.ts`: 데이터 검증과 상태 전이 테스트

기본 실행은 `NEXT_PUBLIC_RESERVATION_DEMO_MODE=true`로 설정했다. 실제 백엔드가 준비되기 전에도 인사이트·디자인 담당자가 모든 상태를 확인할 수 있게 하기 위한 결정이다. 동시에 실제 API로 교체할 위치를 Gateway 하나로 제한했다.

### 2.2 음성 입력과 화면 상태

음성 입력은 API 키가 없는 브라우저에서도 시연할 수 있도록 Web Speech API의 한국어 음성 인식을 사용했다. 지원하지 않는 브라우저, 듣는 중 상태, 오류 메시지, 텍스트 입력 대체 경로를 함께 구현했다.

예약 화면은 다음 상태로 나눴다.

```text
요청 입력
  → 전화 전 추가 확인
  → 요청 검토
  → 전화 연결
  → ARS 진행
  → 상담사 연결 대기
  → 상담 진행
  → 사용자 선택 필요
  → 완료 또는 실패 결과
```

주요 구현 파일은 다음과 같다.

- `ReservationApp.tsx`: 전체 화면 상태 조정
- `ReservationRequestForm.tsx`: 자연어 대화와 상세 정보 수집
- `ReservationReview.tsx`: 전화 전 요청 검토와 추가 선택
- `ReservationProgress.tsx`: 통화 단계, 대화 기록, 사용자 확인
- `ReservationResult.tsx`: 처리 결과, 요약, 전체 기록
- `ChoiceQuestion.tsx`: 선택형 질문과 직접 입력
- `ProgressRail.tsx`, `StatusBadge.tsx`, `Transcript.tsx`: 상태와 통화 기록 표시

### 2.3 디자인 시스템 적용

사용자가 전달한 `디자인.md`를 시각 계약으로 읽고 저장소의 `DESIGN.md`로 정리했다. 색상, 타이포그래피, 간격, 모서리, 그림자, 상태 색, 반응형 규칙을 CSS 변수와 재사용 컴포넌트로 적용했다.

처음에는 업무용 폼 중심 화면을 만들었지만, 사용자 요청으로 뤼튼처럼 대화 중심인 화면으로 다시 설계했다.

- 데스크톱: 왼쪽 사이드바, 중앙 대화 영역, 하단 입력창
- 모바일: 상단 메뉴와 열고 닫을 수 있는 내비게이션
- 자연어 요청을 보내면 AI가 필요한 정보를 한 항목씩 질문
- 기존 검토·ARS·상담·사용자 확인·결과 상태는 대화 흐름 뒤에 유지

`AppHeader.tsx`, `AppSidebar.tsx`로 공통 내비게이션을 분리했고, `Button`, `Field`, `Surface`, `StatusBadge` 등의 공통 컴포넌트를 만들었다. `/design-system` 경로에서는 주요 토큰과 컴포넌트 상태를 한 번에 확인할 수 있게 했다.

## 3. 시행착오와 반복 수정

### 3.1 실패하는 테스트에서 시작

테스트를 먼저 추가했을 때 `schema.ts`와 `demo-timeline.ts`가 아직 없어 두 테스트 파일이 모두 `Cannot find module`로 실패했다. 이후 타입, 스키마, 데모 상태 전이를 구현했고 동일 테스트가 10개 통과로 바뀌었다. 구현이 테스트를 따라 들어간 과정이 원본 세션에 남아 있다.

### 3.2 TypeScript의 지나치게 좁은 리터럴 추론

폼 초기값에 `as const` 성격의 값이 적용되어 `placeName` 등이 빈 문자열 리터럴 타입으로 추론됐다. 사용자가 값을 입력하면 `setState`가 `TS2345`를 발생시켰다. 폼 상태를 명시적인 입력 타입으로 선언하고 날짜 처리도 함께 보정한 뒤 `tsc --noEmit`을 다시 통과시켰다.

### 3.3 디자인 문서 대비 누락된 상태

첫 화면 검수에서는 형태는 정돈됐지만 중요한 기능 세 가지가 빠졌다는 판정을 받았다.

- 전화 전 추가 확인 질문과 선택 버튼 없음
- 통화 중 사용자가 답할 수 있는 강조 확인 카드 없음
- ARS 진행과 상담사 연결 대기 상태 없음

`ChoiceQuestion` 컴포넌트, 재개 가능한 사용자 확인 상태, ARS·대기 상태를 추가하고 데모 타임라인과 화면을 함께 수정했다. 모바일에서 확인 카드가 화면 아래로 밀리는 문제도 하단 작업 영역 배치를 조정해 해결했다.

### 3.4 한국어 줄바꿈 문제

375px 화면에서 “전화 시작”, “확인해 주세요” 같은 문구가 의미 단위 중간에서 갈라졌다. 설명, 알림, 대화 말풍선, 결과 문구에 한국어용 `word-break: keep-all`과 컨테이너 크기 규칙을 적용하고 375·768·1280px 화면을 다시 확인했다.

### 3.5 결과 시각 의미 오류

브라우저 전체 흐름 검증 중 예약 결과 화면이 “예약 확정 시각”이 아니라 “전화가 끝난 시각”을 표시하는 문제를 발견했다. 화면만 보면 성공처럼 보이지만 사용자에게 잘못된 결과를 전달하는 오류였다. 결과 모델이 요청한 예약 시각을 표시하도록 수정하고 회귀 테스트를 추가했다.

### 3.6 폼 중심 화면에서 대화형 화면으로 재구성

초기 버전은 한 화면에서 모든 필드를 채우는 폼이었다. 사용자가 뤼튼과 같은 대화형 챗봇을 요청해 요청 수집 방식을 바꿨다. 자연어 요청을 첫 메시지로 받고, AI가 필요한 정보를 순차 질문한 뒤 기존 검토·통화 흐름으로 넘기도록 컴포넌트를 재구성했다.

### 3.7 실제 지원 범위와 화면 약속 불일치

독립 검수에서 빈 화면의 예시가 병원 예약 변경과 인터넷 설치까지 지원하는 것처럼 보이지만, 모든 입력이 식당 예약 필드로 이어지는 문제가 발견됐다. 실제로 구현하지 않은 범용 LLM 라우팅을 꾸며내지 않고, 예시와 랜딩 문구를 현재 실행 가능한 식당 예약으로 제한했다.

### 3.8 시간 예측과 검수 범위 조정

검수 항목을 계속 추가하면서 사용자에게 안내한 2~3분을 넘겼다. 사용자가 반복해서 남은 시간을 물었고 추가 검수 중단을 요청했다. 이후 진행 중이던 비필수 하위 검수 세션을 중단하고, 이미 완료한 테스트·빌드·브라우저 증거를 기준으로 결과를 전달했다. 기능 검증과 독립 검수의 범위를 처음부터 분리해 안내해야 한다는 교훈을 얻었다.

## 4. 오류 복구

### 4.1 문서 렌더링 도구 부재

PDF 검토 중 Poppler가 없어 첫 렌더링이 실패했다. 설치된 PDF 라이브러리와 macOS 렌더링 경로로 전환해 전체 6페이지의 텍스트와 표를 확인했다. 로컬 HTML은 연결된 브라우저 인스턴스가 없어 실제 렌더링을 확인할 수 없었고, 이 한계를 밝힌 뒤 HTML 본문과 표 구조를 직접 분석했다.

### 4.2 LSP 미설치

TypeScript와 Biome LSP가 설치되지 않아 편집 직후 진단 도구가 실행되지 않았다. 이를 성공으로 간주하지 않고 `vitest`, `eslint`, `tsc --noEmit`, Next.js 프로덕션 빌드로 대체 검증했다.

### 4.3 원격 `main` 강제 갱신과 통합 충돌

push 직전 `git fetch`에서 원격 `main`이 다른 개발자의 백엔드/MCP/ClawOps 작업으로 강제 갱신된 사실을 발견했다. 로컬 변경으로 원격을 덮지 않고 다음 순서로 복구했다.

1. 웹 변경만 `40f656c`로 로컬 커밋
2. 최신 `origin/main`에서 `publish-web` 브랜치 생성
3. 웹 커밋을 cherry-pick
4. `package.json`, `package-lock.json`, `vitest.config.mts` 충돌 해결
5. 원격의 MCP·ClawOps·WebSocket 의존성과 프론트의 UI·검수 의존성을 모두 보존
6. 통합 결과를 `5e47569`로 커밋

강제 push는 사용하지 않았다.

### 4.4 존재하지 않는 OpenTelemetry peer 버전

통합 후 일반 `npm install`은 `@teamlearners/clawops@0.32.0`이 `@opentelemetry/api >=1.20.0`을 요구해 `ETARGET`으로 실패했다. 해당 버전은 레지스트리에 존재하지 않았다. 원격 패키지를 제거하거나 버전을 임의 변경하지 않고 `npm install --legacy-peer-deps`로 기존 의존성을 보존해 잠금파일을 재생성했다. 이후 641개 패키지 감사에서 취약점 0개가 보고됐다.

### 4.5 개발 서버 중복

수동 HTTP 검증을 위해 3020 포트에 새 개발 서버를 실행했지만 기존 3000 포트의 Next.js 서버가 이미 실행 중이라 두 번째 서버가 종료됐다. 기존 서버가 동일 저장소를 가리키는지 확인한 후 그 서버에서 `/`, `/call`, `/design-system`을 요청해 모두 HTTP 200을 확인했다.

### 4.6 GitHub 403과 초대 미수락

첫 push는 현재 로그인 계정에 저장소 쓰기 권한이 없어 HTTP 403으로 실패했다. SSH 키도 없어 우회할 수 없었다. 사용자가 권한 추가 후 다시 요청했지만 같은 오류가 발생해 GitHub API에서 대기 중인 저장소 초대를 조회했다. Write 초대가 발송됐지만 수락되지 않은 상태임을 확인하고 초대를 수락한 뒤 일반 push에 성공했다.

## 6. Codex 활용에서 얻은 교훈

- 음성 AI와 전화망을 같은 기술로 취급하지 않고 통신, 실시간 대화, 업무 판단, 제어 인터페이스를 분리해야 한다.
- 다른 개발자와 병렬 작업할 때는 구현보다 타입과 API 경계를 먼저 고정하는 편이 충돌을 줄인다.
- UI 검증은 예쁜 화면뿐 아니라 실제 도달 가능한 상태, 한국어 줄바꿈, 화면이 약속하는 지원 범위까지 포함해야 한다.
- 실패한 테스트, 타입 오류, 외부 패키지 오류, Git 권한 문제를 숨기지 않고 원인과 복구 방법을 남기는 것이 재현성과 팀 협업에 도움이 된다.
- 장시간 검수에서는 구현 완료와 추가 독립 검수를 분리해서 시간과 완료 조건을 명확히 안내해야 한다.
